The practical guide

Keep many agents
in one place.

Meringue sits above the coding agent CLI you already use. It keeps projects, issues, workers, questions, worktrees, and logs visible while the underlying agent does the coding.

Install & update

Meringue needs Git, Ruby 3.1+, and a signed in coding agent CLI. The installer clones the source to ~/.meringue/src, installs dependencies, and writes the meringue shim to ~/.local/bin.

INSTALL 
curl -fsSL https://raw.githubusercontent.com/jackson-lafrance/meringue/main/install.sh | sh

Run meringue from the repository you want to work on. Run the installer again to update. It only manages files under ~/.meringue and ~/.local/bin. To install from source instead:

FROM A CLONE 
git clone https://github.com/jackson-lafrance/meringue.git
cd meringue
bundle install
bundle exec ruby -Ilib bin/meringue

/update updates a clean source checkout and reloads; /reload restarts without updating. Configuration and state live outside the source in ~/.meringue/. MERINGUE_BRANCH selects a tracked branch for updates.

Quick start

  1. Install and sign in to Pi, Claude Code, or Codex CLI yourself.
  2. Start meringue in a repository. First run Setup asks for a harness, theme, and optional experiments.
  3. Describe a goal in plain English. Meringue registers the project when the goal is routed, creates or reuses an issue, and starts a worker in its own worktree.

Try the populated dashboard without a harness or agents:

DEMO 
meringue demo

Use /glossary for vocabulary and /help for the live command inventory.

Bring your own coding agent

Meringue has no default backend: nothing runs until one is named. Setup reports which supported CLIs it can find, but it does not install or authenticate them.

Pipi · managed transport
Claude Codeclaude · interactive PTY
Codex CLIcodex · interactive PTY

Choose one for both roles or split head and worker backends in /config. Supported aliases include claude_code, claude-code, cc, codex-cli, codex_cli, and openai-codex. Select at runtime with:

SELECT A HARNESS 
meringue tui --harness claude
meringue tui --head-harness claude --worker-harness codex

Pi uses a managed RPC transport. Claude Code and Codex run in native interactive PTYs, so focusing them attaches to the existing process rather than interrupting it. Provider specific details and session behavior are in interactive harness backends.

The core workflow

  1. Prompt. Type a goal in the dashboard chat.
  2. Head. A short lived head reads lightweight context and proposes structured kernel commands.
  3. Issue. The kernel creates or reuses the durable goal and attaches it to a project.
  4. Worker. A worker receives the assignment, harness, and isolated worktree.
  5. Observe. AgentTree rows show projects, issues, workers, and questions; structured logs show meaningful progress.
  6. Continue. Follow ups normally start a fresh worker chained to the previous one, inheriting its worktree and report. Jump into a focused workspace only when sustained direction or deeper transcript visibility helps.

The kernel is the only layer that mutates orchestration state. A worker can change project files; the head routes work but does not perform it.

Commands

Slash commands bypass the head and use the same validated kernel command path. IDs are case insensitive; paths, provider names, models, and themes are not.

/project add <path> [name]Register a repository./issue create <project_id> "<title>" ["<description>"]Create an issue manually./worker spawn <issue_id> "<prompt>"Start a worker for an issue./worker pause <agent_id>Pause a resumable worker turn./worker resume <agent_id>Continue that same session./prompt <agent_id> "<message>"Follow up or retry a worker./jump [agent_id]Open focused workspace navigation./model [head|worker] <provider/model>Set model defaults for future sessions./thinking [head|worker] <level>Set future reasoning defaults./theme [name]Pick or set a colorscheme./configEdit validated settings./prune · /recountClean resolved records or compact IDs.

Also useful: /setup, /questions, /answer, /harness, /models, /keybind, /prs, /reload, /update, and /quit. See the complete command reference.

Configuration

Use /config for the settings editor, or place TOML at ~/.meringue/config.toml. Use --config PATH for one run. A checked in starting point is fixtures/config.example.toml.

CONFIGURE A HARNESS 
[harness]
provider = "claude"
# head_provider = "claude"
# worker_provider = "pi"

[harness.claude]
command = "claude"

Environment variables override config and CLI selection: MERINGUE_HARNESS, MERINGUE_HEAD_HARNESS, and MERINGUE_WORKER_HARNESS. Keep API keys in the provider’s normal authentication flow, not TOML. Configuration and state details are covered in config and settings.

Models & thinking levels

Defaults apply to future sessions, not existing ones. Use role specific values when heads and workers need different budgets:

FUTURE SESSIONS 
/model head anthropic/claude-opus-5
/model worker openai/gpt-5.6-sol
/thinking head low
/thinking worker max

Thinking levels are off, minimal, low, medium, high, xhigh, and max. Meringue stores portable provider/model-id references, while each harness translates the model and reasoning setting into its own flags. /models asks the selected harness for its authoritative catalog; /models refresh fetches it again.

Configure a shared default with model and thinking_level, or role overrides with head_model, worker_model, head_thinking_level, and worker_thinking_level. See session settings for scope, catalogs, and clamping.

Themes

The default meringue scheme uses the yellow, white, green, red, cyan, and purple palette used by the dashboard. Other supported schemes are rose-pine, tokyonight, gruvbox, catppuccin, and kanagawa.

Run /theme to preview, or /theme kanagawa to save. Set [tui] colorscheme = "meringue" in TOML. NO_COLOR=1 removes styling while keeping status, IDs, and structure readable.

Workspaces & keybindings

Isolated workers use dedicated editable Git worktrees and branches. A follow up on the same goal can reuse the settled predecessor’s worktree; two live sessions never share one. The optional focused workspace offers an agent transcript, terminal, editor, and verified PR view.

Dashboard essentials: Tab changes focus, Enter starts jump mode, Esc clears selection, Ctrl-B opens a delivery PR, and Ctrl-C clears input or quits when empty. In a focused workspace, the default leader is Ctrl-Space: then t terminal, f transcript filter, a agent session, b editor, p PR, or q quit.

Customize under [tui.keybindings]; omitted actions retain defaults and an empty list unbinds one. The full interaction model is in keybindings.

Extensions & customization

Meringue keeps provider specific behavior behind the harness client boundary. A new backend supplies session start/resume, prompting, event reading, aborting, and optional focus behavior without changing the kernel or TUI. Pi worker extensions can also provide models; keep the matching --extension flag in the provider’s extra args so catalog probes and real sessions agree.

Teams with many worktrees can opt into a private command worktree provider through [workspace]; Meringue still owns branch reservation, validation, and cleanup. Themes, keybindings, shell/editor launchers, worker command blacklists, experiments, and sparse workspace profiles are configuration paths, not separate plugins. Start with configuration and harness integration.

Troubleshooting

Start here:

DIAGNOSTICS 
meringue doctor
  • Command not found: add ~/.local/bin to PATH, or run bundle exec ruby -Ilib bin/meringue from a clone.
  • Harness missing: check command -v pi, command -v claude, or command -v codex; configure an absolute provider command or its PATH when launched from a restricted environment.
  • No harness configured: run /setup, /harness, or pass --harness. Meringue intentionally refuses to guess.
  • Worker blocked: inspect its error with /info <agent_id>; free disk space for checkout failures, then prompt the worker to retry.
  • GitHub actions unavailable: enable GitHub support in Settings → Experiments, then use /github test. It is without write access.

Do not delete state to repair an ordinary runtime issue. The session reconciliation and workspace recovery references explain safe recovery.

Architecture

The flow is deliberately small:

prompt → stateless head → kernel commands → JSON state
                         ↓
                 worktree + harness worker → AgentTree and logs

The kernel validates commands, owns orchestration state, provisions workspaces, and records logs. Heads route or ask questions. Harness clients translate backend behavior into generic session operations. The TUI renders state and provides navigation; it never repairs state or deletes worktrees. Source files reopen focused Ruby classes by command family and dashboard surface, keeping the implementation navigable.

Read AGENTS.md for the architecture contract and the lib source for implementation boundaries.

Contributing

Read AGENTS.md before changing the repository. Keep slices small, preserve the kernel/TUI/head/harness boundaries, and add hermetic Minitest coverage for behavior changes. The suite uses only Ruby, Rake, and Minitest:

VERIFY A CHANGE 
rake test
git diff --check

Use a task branch, avoid network and real harnesses in tests, and write only inside temporary directories. For the full testing boundaries, see testing.md. Issues and pull requests live on GitHub.
